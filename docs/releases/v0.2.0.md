# Release v0.2.0

**Recurrence rules, durable records with use restrictions, durable indexes and
data acquisition: four proposed contract families, and a release-identity
process decision.**

This is a minor release because it adds new contract families and a new major
version of an existing one. Every new family is proposed. No implementation,
store or backend is qualified by this release.

## Highlights

### Recurrence rules (`recurrence/v0`, proposed)

A canonical JSON form for a frozen subset of the RFC 5545 recurrence rule, with
normative expansion semantics and one pinned conformance corpus.

- **Subset:** `MINUTELY` to `YEARLY`; `BYDAY` with ordinals, `BYMONTHDAY`,
  `BYMONTH`, `BYSETPOS`, `BYHOUR`, `BYMINUTE`; `INTERVAL`, `COUNT` or `UNTIL`,
  `WKST`; `DTSTART` as a local civil time with an IANA time-zone name; one
  `RRULE` plus `RDATE` and `EXDATE`. Unsupported parts are refused, never
  ignored.
- **Time zones:** a generated time that falls in a DST gap is skipped, consumes
  no `COUNT` and is a non-slot, never recorded as missed. An explicit time in a
  gap uses the pre-gap offset; an overlap resolves to its first instant.
- **Bounds:** `UNTIL` is inclusive; queries are half-open; `EXDATE` removes rule
  and `RDATE` instances alike, and `COUNT` is taken before exclusion.
- **Identity:** normalization then JCS, with a `sha256` digest. Time-zone names
  are kept as written from a pinned accepted set, so a location name does not
  change identity when the tz database relinks it.
- **Corpus:** hand-derived accept and reject vectors, pinned by digest to IANA
  tzdb 2026e, with transition evidence citing the release's source lines.
  Conformance is claimed per (corpus digest, tzdb version).

The repository's checker is an independent verifier: it never writes expected
values and reads no host time-zone data. Promotion requires two independent
implementations to pass the corpus and a recorded decision.

### Durable records with use restrictions (`durable-record/v1`, proposed, experimental)

`durable-record/v1` adds `tombstoned` and `untombstoned` journal entries, which
the v0 standard defines as a breaking change, so this is a new major contract
version. The v0 schemas and semantics are unchanged.

- A hold targets a record, an exact revision or a shared body, with a reason,
  an evidence reference and an observation time. Several holds may coexist;
  restoration removes one identified hold.
- Serving, export and reuse require authoritative protection state at a current
  cut and fail closed otherwise. There is no audit export bypass.
- v1 reuses the v0 record envelope and revision digests. A v1 reader refuses v0
  journals and receipts. There is no automatic migration: a v0 stream stays v0,
  and an adopter needing holds opens a separate v1 stream.

v1 stays proposed and experimental until an independent reader agrees with its
vectors with no known disagreements and an adopter qualifies a store
([ADR-0019](../decisions/ADR-0019-durable-record-tombstoning.md)). The current
checker reuses v0 helpers and does not meet the independent-reader gate.

### Durable indexes (`durable-index/v0`, proposed, experimental)

Object-inventory snapshots as a profile of `segmented-snapshot/v0`, with index
row, plan, metadata, publication and identity-cutover schemas.

- Observation plans use a length-framed semantic digest over canonical
  unicode-prefix scopes.
- Only confirmed-complete, gap-free scopes authorize absence-derived tombstones;
  a reduced scope requires an acknowledgment bound to the exact parent and plan.
- A changed index-set identity needs an explicit cutover to a new baseline.
- An independent TypeScript reader, sharing no code with the Python checker,
  checks the plan and transition vectors. Its known-disagreement list is empty
  at this release.

Evidence is logical only. Physical Parquet twins and a physical reader are
adoption gates; no physical reader, producer or storage backend is qualified,
and composition does not ratify `coverage-attestation/v0`
([ADR-0017](../decisions/ADR-0017-durable-index-contract.md)).

### Data acquisition (`data-acquisition/v0`, proposed)

Source policy, acquisition plan and registration result schemas, with exact-byte
digest pins, attributed scope compromises and explicit unavailable and
indeterminate outcomes. Allocation intervals are half-open with an aggregate
span ceiling; replay and request identity are scoped to entity and source
across authority epochs. Registration records capacity; runtime admission and
adopter qualification remain separate
([ADR-0014](../decisions/ADR-0014-data-acquisition-contract.md)).

### Release public identity (PDR-0008, proposed)

A process decision generalizing PDR-0004's committed-key-pin posture into
controls any repository can adopt: public pins are committed blobs read from
the tagged commit, one designated checker derives fingerprint anchors with no
second parser, the ceremony binds its checker and tag as explicit inputs with
no fallback, and third-party verification keys are committed, origin-named
files. This repository is not yet conformant; it adopts in a separate tooling
change.

## Schema revision

`segmented-snapshot/v0/snapshot-manifest.schema.json` gains an optional,
digest-bound `profile_metadata` binding under the same `$id`. Existing manifests
keep their meaning and remain valid. A reader that does not implement
`profile_metadata` must refuse a manifest that contains it, including on
selective reads.

## Charter

PDR-0006 gains Rule 2c: Python >= 3.9 and Node.js >= 22.6 are the named
validation interpreters for contract tooling, TypeScript tooling uses erasable
syntax only, and a validation tool imports only its standard library and runs
with no install step. Contract tooling is limited to establishing compliance;
benchmarking and load testing belong in separate repositories using synthetic
data only. A known disagreement between an independent checker and the vectors
must be resolved before the next tagged release.

## Toolchain and CI

- Goneat v0.6.5 and the glibc tools runner v0.5.12, consumed by immutable
  digest. The image carries biome 2.5.15; `biome.json` migrates the deprecated
  `linter.rules.recommended` to `"preset": "recommended"`. Repositories with
  TypeScript that adopt this runner should expect biome formatter changes.
- Windows contract shards set up Node.js, and the shard guard requires every
  TypeScript tool to run in exactly one shard.
- The release-surface guard and the tag script no longer pipe into `grep -q`
  under `pipefail`, which could turn a match into a false failure on a large
  changelog.

## Upgrade notes

- Pin consumers of `segmented-snapshot/v0` should confirm their readers refuse
  manifests that carry `profile_metadata` if they do not implement it.
- `durable-record/v0` adopters are unaffected; adopting v1 means opening a new
  v1 stream.
- No existing contract version changes meaning.
